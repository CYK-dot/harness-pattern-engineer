# 模式

> **何时读我**：准备编写、修改或评审任何一份"模式"时——包括本认知工程自己的每一份模式。

---

## 1. 诉求与第一性

通过模式组织认知工程，提升harness组件效率，降低人与AI助手交互的成本。

### 1.1 认知的浪费

每一次让AI助手完成一件有难度的事，我们都在重新描述它：重新描述目标、约束、做法、什么算做得好。这些描述里大部分是重复的。换个对话、换个模型、换个项目，又得重来一遍。

**认知没有被积累，它被一次次地消耗掉了。**

### 1.2 为什么不能直接写成程序 / 结构化格式 / 自然语言

| 载体 | 为什么不行 |
|---|---|
| 程序 | 程序解决确定性问题；认知处理的是判断、取舍、解释、创造。硬写成程序，就丢掉了它对模糊情境的敏感。 |
| JSON / YAML / 工作流 | 语法上已经预设了认知的形状，与人的思考方式不一致；人仍旧要先把自己的想法转成格式。 |
| 自然语言 | 最自由，但同一段意思十个人写出十种结构。AI助手读得懂，工具链接不住。 |

所以需要一种**中间物**：比自然语言规整，比编程语言少一层转义；**所写即所得**——交给新人或交给AI助手，都能发挥作用。

### 1.3 认知工程

把"给人读的知识 / 意图"**编译**成"AI助手可直接消费的形态"，这件事本身是一门工程：

- **源**：模式。人机可读、平台无关；
- **产物**：某个平台上的 skill / agent / 工具。只服务机器，并带上平台细节（路由摘要、加载路径、权限……）；
- **编译**：把"需要被理解的认知"**沉降**成"可以被直接使用的认知"——落成触发条件、使用边界、失败处理；
- **改源不改产物**——产物是编译结果，要改就回源改，然后重编。

正如软件工程由一层一层的树状模块构成，模块与模块之间的交互构成了复杂的软件系统。认知工程也使用模块组装，每个模块称为一个**模式**。

### 1.4 模式是什么

各领域都在用"模式"这个词，含义却高度一致。

**（一）模式识别：学科里的模式**

模式识别研究的，是怎么从纷繁的输入里**认出**它属于哪一类已知情形。它不关心"这一个具体的东西是什么"，而关心"它像哪一类"。
在这个学科里，**模式 = 某一类情形的共同表征**。它的价值在于：一旦归入某类，就可以调用该类的处置方式，不必从头分析每一个细节。

医学是最老的例子：发烧、皮疹、关节痛，单看都不是结论；一旦认出这是某个**症候群**，处置路径立刻清楚。"症候群"（syndrome）就是医学给"一组症状构成的模式"起的名字。

**（二）程序设计：设计模式**

程序员说的设计模式，是一类反复出现的设计问题、连同它的解法骨架，而且**有名有姓**。

- 名字是第一位的：说"这里用 Observer"，比花十分钟解释松耦合机制更省。
- 模式只给骨架，不给血肉：同一个 Observer，可以用在 GUI 事件、日志分发、配置热更新上，各写各的。

**（三）建筑学：模式的源头**

Christopher Alexander 在《建筑模式语言》里给的定义，至今最准：

> 模式描述了一个在我们的环境中反复出现的问题，然后描述了解法核心——以这样的方式：你可以无数次地使用它，而不必两次用同样的做法。

两个要点都在里面：**反复出现的问题** + **解法核心**，且**可复用而不重样**。

**（四）共同点**

把上面放到一起，各领域的"模式"都在做同一件事：

| 要素 | 说明 |
|---|---|
| 一个**反复出现的情形** | 不是一次性事件；第二次、第一百次遇到，都认得出来 |
| 情形的**处置核心** | 不是完整的方案，而是方法论。它告诉了阅读者在碰到此类情形后如何思考、如何行动 |
| 一个**名字** | 让它被认出、被说出、被传递——而不是被推导 |

### 1.5 为什么用"模式"来组织认知工程

**模式**是认知的最小可复用单元——一段被工程化了的认知。它不教你"第一步做什么"，它说的是这件事的立足点、判断依据、概念的用法、历史的教训、成立的标准。
一个新人读了它，不会立刻知道怎么下手，但会知道往哪个方向想；做上几次，这份能力就会在他的脑子里扎根。AI助手读了它，也是同样的效果。

换言之，模式天然可被认出，而**人和AI助手调用经验与方法论的机制，本来就是模式识别**：先认出"这像我遇到过的东西"，再由它检索到相应的经验与方法论，加载进当前的工作记忆。
所以把认知组织成模式，就是让文字直接对接这套机制。

Alexander 把成组的模式称为"语言"，缘由正在于此：它们可以像词汇一样被反复取用、彼此组合，而不必每次从头说明。

**一段符合"模式识别"的文字，传递信息的开销极低——几乎能很快读懂。无论方向是人给AI助手、AI助手给人，还是人给人、AI助手给子代理。**
因为读者不必先建立一套你的分类体系，只需要**认出**；认出来了，后面的内容就落进已有的槽位。

## 2. 效果

用模式组织认知工程之后：

- **认知开始积累。** 同一类判断只被想清楚一次；换对话、换模型、换项目、交接工作，直接取用，不再重新描述。
  - 信号：同类判断第二次出现时，有人直接引用模式名，而不是重新描述一遍。
- **沟通成本趋近于零。** 接手者读完就知道往哪里想、什么算做成。越是"想法一致"的接手者（人、或AI助手），越接近零成本。
  - 信号：接手者读完前两类组成就能决定用不用，不再追问"你到底想解决什么"。
- **更抗过时。** 写进去的是诉求、取舍与纪律——模型再强也不会替你做的判断；不是能力，也不是实现细节。概念边界与适用场景仍会变，但比实现细节慢得多。模型越强，它越像助力，而不是累赘。
  - 信号：回看历次改动，动的是例子与平台细节；诉求、边界与取舍没有动过。
- **缓存友好。** 黑盒短，可以快速扫过；白盒大，只在需要时展开。常驻位只留一个最便宜、最不可缺的锚。
  - 信号：接手时只需记住那一条"终"，其余部分按需取用，不必重读全篇。

## 3. 概念与方案推导

### 3.1 核心概念

| 概念 | 含义 |
|---|---|
| 模式 | 一段被工程化了的认知，认知的最小可复用单元。 |
| 模式名 | 模式被认出、说出、引用的钩子。 |
| 黑盒与白盒 | 黑盒是一个模式的对外契约：它解决什么问题、用了它能带来什么；白盒是一个模式的内部构造：有哪些概念、如何工作、为什么这样工作。 |
| 自顶而下 | 一种从黑盒到白盒、从目标到手段的思想，旨在降低认知负担。模式总是自顶而下组织。 |
| 第一性 | 一种使用自顶而下思想的思考方式。先思考无论诉求如何变化，有哪些东西是不变的？然后思考基于这些不变的诉求，能推演出哪些不变的解决方案？ |
| 渐进披露 | 一种旨在降低认知负担的表述技巧。先只展示最重要、最常用或当前必需的信息，把次要、复杂、高级的信息隐藏起来，由读者按需发掘。 |

### 3.2 一个模式的结构

本文采用一种组织观点：人与AI助手在解决问题时，通常依次考虑四件事——
1. 需要解决的问题是什么。
2. 这件事是否值得投入。
3. 采取某种做法的依据是什么。
4. 具体如何实施，以及完成的标准是什么。

例如一次周末宴请朋友：
> 周末宴请朋友，首先要确定这次聚会的性质：是普通聚餐，还是久别之后的叙谈。二者对应的安排不同——前者在餐馆即可解决，后者需要一个不受打断、可以久坐的场所。这一步若有偏差，后续安排都会偏离目标。
> 其次要判断投入的规模：叫外卖、外出就餐，还是在家准备。三种方式各有代价，需要权衡之后才能决定。
> 决定在家准备之后，才轮到依据的问题：菜单为什么要在采购之前确定，主菜为什么只保留一道。
> 最后是实施与验收：前一天处理需要泡发的食材，当天先炖后炒。验收的标准不是菜品的数量，而是客人饭后是否仍愿意留在桌旁交谈。
>
> 四件事依次出现，不能跳过，也不能调换：前一件事的结论，决定后一件事是否值得考虑。

写作有一条通行的原则。SICP 的序言里写道，程序首先是写给人读的，其次才是给机器执行的。模式同样如此：它的价值取决于读者能否读下去，因此顺序必须迁就读者。

据此给出模式的结构定义：一个模式由一份文档，或者多份文档构成。但无论其如何组织，总是要按照下述顺序让读者访问。

| 组成 | 地位 | 内容 | 读完应能回答 |
|---|---|---|---|
| 1 诉求与第一性 | 黑盒 · 输入契约 | 它要解决什么问题。事故、反例、味道、场景等皆可放，形式不限 | 它解决什么问题？ |
| 2 效果 | 黑盒 · 输出契约 | 用自然语言讲清"用了它之后能带来什么"，并给出可观察的有效信号 | 值不值得用？ |
| 3 概念与方案推导 | 顶层白盒 | 有哪些概念、如何工作、为什么这样工作 | 它怎么运作？ |
| 4 实操与评判标准 | 实现层白盒 | 具体怎么做——命名、常驻、拆分……；以及做完之后怎么评 | 我该怎么做，做成什么样算好？ |

这四类组成分为两层。
前两类是**黑盒**。读者在决定是否继续往下读之前，只关心它解决什么问题、能带来什么结果；因此，用于决策的材料必须置于最前。
后两类是**白盒**，而白盒本身也分两层。靠近前面的部分是**概念与方案推导**：它离目的较近，稳定，可以写死。
再往下是**实操与评判标准**：它离手段较近，会随工具、平台和模型能力变化，应写成按需查阅的形式。

## 4. 实操与评判标准

### 4.1 好的诉求与第一性，读者能认出，漂移能查住

诉求要写成读者一眼认得出的处境。Alexander 说模式描述的是"在我们的环境中反复出现的问题"——既然反复出现，读者多半已经遇过它，要做的只是让他认出来。抽象名词做不到这一点：

> 反例："本模式解决设计过程中的信息不同步问题。"
> 正例："契约还没定，就有人开始写实现了。"

正例里没有出现"沟通""协同"这类词，却精确指向一种处境；读者读到它，能想起自己上一次这么做是什么时候。判据正是这一条：读完的人能说"对，就是这个问题"。若本模式不覆盖某些情形，一并写明，以免误用。

第一性写成一两句话，回答三件事：正在做什么，为什么做，做到什么算成。它是否合格，可以拿一次具体的取舍去套：

> 面对"现在要不要把这一节拆出去"，"让同一类判断只被想清楚一次"能给出方向——拆，是为了让读者不必同时记住太多东西；
> 而"提高文档质量"给不出方向，它只是把原话换了个说法。

它必须常驻，因为它的职责是查漂移，而漂移可能出现在任何一步判断上；等到需要时再去翻，往往已经偏离很远。缓存只有一位，这一位应当留给它：它最短，也最不可缺。每个模式都自带第一性，这就是分级锚定——那句"终"放进每一份模式的开头，无论读到多深，抬头都能看见它。有父模式时，两句话要能连成一条线；若两句重复，说明这个子模式没有自己的立场。

### 4.2 好的效果，每条都配一条可观察的信号

效果要写成读者能拿去判断的样子。没有信号的表述只是口号：

> 反例："沟通成本降低。"
> 正例："同类判断第二次出现时，有人直接引用模式名，而不是重新描述一遍。"

正例写清了三件事：谁、在什么场景、看到什么。出现没出现，一眼可见；反例无从判断，也无法支撑决策。

《重构》把"先有一套可靠的测试"列为动手的前提：没有能立刻验证的手段，任何改动都只是赌。效果与信号的关系也是如此——信号就是那份随时可取的验证。配不上信号的，通常不是效果，而是机理，应当移到第 3 类组成。判据同样只有一条：读完第 2 类组成，读者能决定"值不值得用"。

### 4.3 好的概念与方案推导，只讲凭什么这么做

这一类组成给的是理由，不是步骤。二者的差别，在于读者读完能不能自己往下推：

> 反例（步骤）："先判断可逆性，再判断代价。"
> 正例（理由）："不可逆的决定做错之后回不了头，而代价随时间放大，所以先判断可逆性。"

反例读起来像命令，读者照做而不知其所以然，条件一变就无从判断；正例给出了依据，读者能自己推出下一步。步骤属于第 4 类组成。概念只定义本模式特有的词，执行者已经会用的词不必解释。

《人月神话》把"概念完整性"列为系统设计中最重要的考虑：宁可省略若干特性，也不要让一套东西里出现彼此不搭的部分。理由讲清楚了，概念才立得住；只给步骤，一致性没有着落。

### 4.4 好的实操与评判标准，写到执行者还不会的地方为止

这一类组成的下界是明确的：再往下分解，一旦进入"执行者自己会做"的领域，就停。越界的部分不但没有帮助，还是整份模式中最容易过时的内容：

> 反例（越界）："用 mkdir 新建一个目录。"
> 正例（不越界）："四类组成各占一节，按 1 到 4 排序。"

前者执行者本来就会，且换一个平台就不同；后者是执行者不会自己想到的约定。判据：真要用的人读完能上手。

### 4.5 公共评判标准

**命名。** 名字应当取自"什么情形下会用到它"，而不是取自内部的实现——后者会随实现换代，前者不会。

> 反例："兼容性处理。"
> 正例："接口要改了。"

反例说的是做法，等做法换代，这个名字就没人再认得；正例说的是处境，处境不变，名字一直可用。

Eric Evans 在《领域驱动设计》里把这种共享的词汇称为**通用语言**（Ubiquitous Language）：同一个系统里，所有参与者用同一套词指同一件事，名字一旦定下，就不再解释。模式名承担的是同一件事。名字要能被完整引用（写作 `模式名`），且一个模式只留一个名字。

**拆分与停止。** 判据不在"某一章有多长"，而在某一处局部是否已经大过它所处的位置。

> 反例："第三章写了 12 页，该拆了。"
> 正例："这一节要求读者同时握住四件事才能读懂，该拆了。"

前者的判据是长度，长度本身不说明问题；后者的判据是读者是否超载。

Fowler 在《重构》里用"坏味道"来指这类征兆：与其先给出定义，不如给出一组可辨认的迹象，见到就知道该动手。下面的五条取的是同一办法。

| 信号 | 说明 |
|---|---|
| 某节超过一屏 | 连续阅读需要滚动，读者开始记不住上文 |
| 你开始想给它起名 | 命名冲动，是"它已经是一个东西"的最早证据 |
| 跨父模式复用 | 同一段白盒被多个父节点需要 |
| 工作记忆超载 | 读者必须同时记住太多概念才能读懂这一节 |
| 变更频率明显不同 | 一部分经常改、另一部分很稳，绑在一起会互相拖累 |

拆分的方式与黑白盒递归相同：新模式的对外契约，就是父模式白盒里的那一块；父模式在搬走的位置只留它的黑盒，和一句"什么时候会走到这儿"。

> "某个模块的黑盒契约，正是更大一级模块的白盒构造。"

**总清单。** 写完或改完，按上面的条目自查：

- **检索**：这份模式会被"什么情形"检索到？那个情形写进第 1 类组成了吗？
- **诉求与第一性**：问题能被认出吗？那句话能查漂移吗？有父模式时，两句话连得成一条线吗？
- **效果**：每条效果都配了可观察的信号吗？读者能决定"用不用"吗？
- **概念与方案推导**：是否混进了"怎么做"——那属于第 4 类组成？
- **实操与评判标准**：是否写到了"执行者自己会做"的地方？对照上面的征兆，该拆的拆了吗？
